# 04. 최소 버전 구현 범위

MVP는 대표 사용자가 핵심 문제 하나를 처음부터 끝까지 해결할 수 있는 최소한의 동작 가능한 버전이다. 이 문서의 범위는 사용자가 합의한 **대학생의 과제 하나 비교**, **날짜별 가능 시간 입력**, **20% 여유 기준 신호등**, **근거 확인과 수정·재계산**을 구현 가능한 기능으로 나눈 것이다. 대표 이용 사례는 실제 인터뷰가 아닌 `02_user.md`의 가상 시나리오다.

## 1. 이번에 구현

| 요구사항 | 선정 이유 | 완료 기준 |
|---|---|---|
| REQ-01 과제·마감·필요 시간 입력 | 비교 대상과 계산 기준이 필요하다. | 과제명, 미래의 마감 날짜·시각, 0보다 큰 남은 예상 작업 시간을 입력해 계산을 시작할 수 있다. |
| REQ-02 날짜별 가능 시간 입력·합산 | 합계만 떠올리는 부담을 줄이고 실제 일정을 돌아보게 한다. | 오늘부터 마감일까지 각 날짜의 해당 과제 시간을 입력한다. `1+2+2`시간이면 가능한 시간 `5`시간으로 계산한다. 오늘과 마감일의 사용 가능 구간을 안내한다. |
| REQ-03 시간 비교·신호등 판정 | 서비스의 핵심 질문에 답한다. | 필요한 시간 N과 가능한 시간 A에 대해 `A<N`은 빨강, `N≤A<1.2N`은 노랑, `A≥1.2N`은 초록으로 판정한다. `N=10`일 때 `A=9.5/10/11.5/12/12.5`는 순서대로 빨강/노랑/노랑/초록/초록이다. |
| REQ-04 판단 근거와 차이 표시 | 색상만으로는 부족한 정도를 알 수 없다. | 상태 이름, N, A, `|A−N|`, 입력한 예상치 기준이라는 안내를 표시한다. `N=8, A=5`면 `3시간 부족`, `N=A`면 `여유 0시간`으로 표시한다. |
| REQ-05 수정·재계산 | 사용자가 시간을 더 확보했을 때 계획의 변화를 확인한다. | `N=8, A=5`에서 날짜별 시간을 수정해 `A=9`로 계산하면 `1시간 여유·노랑`으로 갱신된다. 수정 중인 입력에 이전 결과가 최신 결과처럼 표시되지 않는다. |
| REQ-06 기본 입력 오류 처리 | 잘못된 입력으로 잘못된 결론을 내리지 않도록 한다. | 빈 과제명, 잘못되거나 지난 마감, `N≤0`, 음수·숫자가 아닌 날짜별 시간을 거부하고 수정할 항목을 알려준다. 모든 날짜가 `0`시간인 입력은 허용하며 N시간 부족으로 판정한다. |
| REQ-07 날짜별 시간 상한 확인 | 오늘과 마감일에 남아 있지 않은 시간을 가능한 시간에 넣지 않게 한다. | 각 날짜의 입력 시간이 현재 시각부터 마감 시각까지 해당 날짜에 실제로 존재하는 시간을 넘으면 계산을 막고 해당 날짜를 알려준다. 같은 날 마감도 처리한다. |
| REQ-08 로그인 없는 기본 사용성 | 과제의 정적 웹앱 조건을 충족하고 바로 시연할 수 있게 한다. | 로그인 없이 입력→계산→수정이 가능하다. 입력마다 이름표가 있고 키보드로 조작할 수 있으며, 좁은 화면에서도 핵심 결과를 읽을 수 있다. |

구현 중 REQ-01·REQ-02의 마감 입력 범위를 **오늘부터 1년 이내**로 한정했다. 날짜별 입력칸이 과도하게 늘어나는 문제를 피하기 위한 선택이며, 1년보다 먼 마감은 이번 버전에서 비교할 수 없다.

REQ-01~08은 합의한 흐름을 완성하는 데 필요한 구현 범위로 선정했다. REQ-06~08은 계산이 올바르고 결과를 이용할 수 있도록 하는 기본 품질 항목이다. 완료 여부는 코드 작성만으로 판단하지 않고 `07_check.md`에 실제 브라우저 조작 결과로 기록한다.

## 2. 보류·제외

| 요구사항 | 구분과 이유 | 사용자에게 미치는 영향 | 이후 재검토 조건 |
|---|---|---|---|
| REQ-09 브라우저 내 입력 저장·복원 | **보류.** 첫 계산과 수정 흐름에는 필요하지 않으며 지난 마감의 입력 복원 규칙까지 설계해야 한다. | 새로고침하거나 다시 접속하면 입력을 다시 해야 한다. | 핵심 흐름을 완성하고 실제 사용자에게 반복 입력이 문제인지 확인한 뒤 검토한다. |
| REQ-10 여러 과제 비교·자동 시간 배분 | **첫 버전 제외.** 과제 하나를 먼저 비교하기로 합의했다. 여러 과제 간 시간 중복과 우선순위 규칙은 별도 문제다. | 사용자가 과제별 가능 시간을 직접 배분해야 하며 여러 과제를 한 화면에서 비교할 수 없다. | 단일 과제 흐름이 검증되고 여러 과제를 함께 다뤄야 한다는 근거가 생기면 검토한다. |

외부 달력 연동, 알림, AI 작업 시간 추정도 이번 버전에 넣지 않는다. 이 항목들은 요구사항 후보 번호를 부여한 기능이 아니므로, 향후 범위에 넣을 때 사용자 문제와 완료 기준을 정의하고 새 번호를 부여한다.

## 3. 선정 기능만으로 핵심 흐름 따라가기

아래 숫자는 **시험을 설계하기 위한 가상 예시**다. 실제 사용자의 경험이나 테스트 결과가 아니다.

1. 대학생 A가 한 보고서의 이름, 미래의 마감 날짜·시각, 남은 예상 작업 시간 **8시간**을 입력한다. **REQ-01**
2. 오늘부터 마감일까지 해당 과제에 쓸 수 있는 시간을 날짜별로 **1·2·2시간** 입력한다. 앱이 **5시간**으로 합산한다. 오늘은 현재 이후, 마감일은 마감 시각 이전만 계산에 포함한다. **REQ-02, REQ-07**
3. 계산을 누르면 `A=5 < N=8`이므로 **빨강**, **3시간 부족**, 필요한 시간 **8시간**, 가능한 시간 **5시간**이 나타난다. 입력값 기준의 판단이라는 안내도 보인다. **REQ-03, REQ-04**
4. A가 실제로 추가 시간을 확보할 수 있다고 판단한 경우 날짜별 입력을 수정해 총 **9시간**으로 만든다. 새 계산 결과는 **노랑**, **1시간 여유**다. `9/8=1.125`이므로 20% 여유에는 못 미친다. **REQ-05**
5. 필수값을 빼거나 마감 후 시간을 입력하면 오류 안내를 보고 수정한 뒤 다시 계산한다. 이 흐름은 로그인 없이 브라우저에서 이어진다. **REQ-06, REQ-08**

이 흐름으로 대표 사용자는 현재 계획의 부족 여부를 확인하고, 확보 가능한 시간을 조정했을 때 판단이 어떻게 바뀌는지 확인할 수 있다. 앱은 추가 시간을 실제로 확보해 주거나 과제 완료를 보장하지 않는다.

## 4. 흐름 점검에서 발견한 설계 과제

- 마감 날짜·시각을 바꾸면 날짜 목록도 바뀌어야 한다. 같은 날짜의 입력은 유지하고 범위 밖 날짜는 계산에서 제외하는 방식이 적절한지 `06_design.md`에서 정의한다.
- 날짜별 입력에 허용할 시간 단위와 소수점, 시간 표시 자릿수를 정해야 한다. 신호등 판정에는 표시용 반올림 전의 값을 사용한다.
- 화면을 오래 열어 둔 경우 현재 시각이 바뀌므로 계산 버튼을 누를 때 미래 마감과 날짜별 시간 상한을 다시 검사해야 한다.
- 가능한 시간은 사용자가 실제로 해당 과제에 배정한 시간이다. 앱은 수업·수면·다른 과제 일정을 알지 못하므로 자동으로 빼지 않는다.
- `02_user.md`는 가상 시나리오다. 실제 사용자의 작업 시간 추정 방법과 날짜별 입력 부담은 향후 확인한다.

## 5. 후속 작업

`05_plan.md`에는 REQ-01~08만 구현 작업으로 연결했다. REQ-09~10은 보류 목록에 남겼다. 사용자가 정한 **하루 2시간 가정**으로 테스트·수정·배포·영상 제작 시간을 확보했으며, 실제 투입 시간은 아직 확인되지 않았다. `06_design.md`에서 위 설계 과제를 구체화했고, 로컬 브라우저 확인 결과는 `07_check.md`에 기록했다.
