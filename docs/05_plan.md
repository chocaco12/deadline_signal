# 05. 구현 계획 — 과제 신호등

> 상태: 실행용 계획 초안. 요구사항 범위는 `04_requirements_mvp.md`의 REQ-01~08을 따른다. 사용자가 **하루 2시간을 사용할 수 있다고 가정하자**고 정했으며, 실제 투입이나 작업 완료를 뜻하지 않는다. 아래 날짜는 목표 일정이다.

## 1. 계획 기준

- 기준일: 2026년 11월 15일. 과제지 표기 마감은 **2026년 12월 11일(금) 밤 12시**다. 정확한 e-class 제출 시각은 사용자가 해당 화면에서 확인한다.
- 목표: **12월 8일까지 제출 자료를 준비**하고, **12월 9~10일을 예비일**로 남긴다. 실제 제출은 사용자가 e-class에서 수행한다.
- [사용자가 정한 계획 가정] 11월 16일부터 **하루 2시간**, 주말을 포함해 필요할 때 사용할 수 있다. 12월 8일까지 23일간 최대 **46시간**, 12월 9~10일 예비일에 최대 **4시간**을 추가로 확보할 수 있다는 계산이다. 이는 실제 작업 기록이나 매일 2시간을 반드시 써야 한다는 뜻이 아니다.
- Codex가 문서·코드 작성, 로컬 실행·오류 수정, 가능한 브라우저 검증을 맡는다. 사용자 판단이 필요한 범위와 실제 경험은 사용자 의견을 반영한다.
- 첫 버전은 과제 **하나**를 대상으로 하며 저장·복원(REQ-09), 여러 과제 비교(REQ-10)는 구현 작업에 포함하지 않는다.

## 4. 의존 관계와 사용자 확인

`W01 설계 → W02~W05 구현 → W06 시험 → W07 수정·재시험 → W08 배포 → W09 영상 → W10 제출 점검` 순서다. 배포된 앱을 기준으로 영상을 찍어 영상과 실제 화면이 어긋나지 않게 한다.

사용자가 직접 확인하거나 수행할 내용은 다음과 같다.

1. 하루 2시간이라는 가정으로 계획했다. 실제로 시간이 부족해지거나 특정 날짜에 참여할 수 없다면 그 시점에 작업 순서와 목표일을 조정한다.
2. 구현 후 실제 과제의 예상 작업 시간과 가능한 시간을 입력해 결과가 이해되는지 관찰한다. 실제 과제 정보를 공개 저장소 문서에 넣지 않아도 된다.
3. GitHub에 올릴 파일 목록과 비밀정보 점검 결과를 확인하고, 업로드와 Pages 설정을 수행한다. GitHub 작업을 별도로 요청하면 그 범위에서 Codex가 대신 진행할 수 있다.
4. 시연 영상을 촬영하고 e-class에 제출한다. 실제 제출 여부는 사용자 확인을 기다린다.

## 6. 변경 관리와 완료 기록

- 구현 범위가 달라지면 이유와 영향을 `03_requirements.md`, `04_requirements_mvp.md`, 이 계획, `06_design.md`, `07_check.md` 중 관련 문서에 반영한다.
- REQ 번호는 단계가 바뀌어도 유지한다. W 번호는 작업을 식별하며 REQ 번호를 대체하지 않는다.
- 실제 시작·완료 날짜, 시험 결과, 배포·제출 여부는 확인 후 기록한다. 현재 어떤 W 작업도 완료로 표시하지 않는다.
