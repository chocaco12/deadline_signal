# 01. 프로젝트 기획서 — 과제 신호등

> 상태: 대학생의 과제 하나 비교와 20% 여유 신호등을 구현했다. 초기의 날짜별 가능 시간 입력은 사용자가 입력 부담을 지적해 2026-11-18 하루 평균 시간 한 칸으로 변경했다. 개별 요구사항의 범위는 `04_requirements_mvp.md`에 정리했다. 실제 인터뷰 결과는 제공되지 않았다.

## 1. 프로젝트명과 소개

**과제 신호등 (Deadline Signal)**

“마감일은 알고 있는데, 지금부터 해도 끝낼 수 있을까?”라는 질문에 답하기 위해, 과제를 끝내는 데 필요한 예상 시간과 마감까지 실제로 사용할 수 있는 시간을 비교하는 웹앱이다. 비교 결과를 신호등과 시간 수치로 보여주어 사용자가 시간 부족 여부를 판단하도록 돕는다.

영어 이름은 기존 대화에서 제안한 표기를 사용하며, 저장소 이름은 사용자가 지정한 `deadline_signal`이다.

## 2. 배경과 필요성

### 확인된 내용

- 사용자는 마감일까지 필요한 시간과 공부 가능한 시간을 비교해 시간 부족을 알려주는 서비스를 만들고 싶다고 설명했다.
- 핵심 질문은 단순히 마감일을 확인하는 것이 아니라, 지금 시작했을 때 끝낼 시간이 있는지 판단하는 것이다.

### 문제에 대한 가정

- [가정] 대학생은 과제 마감일을 알고 있어도 남은 작업량을 시간으로 환산하거나 수업·약속 등을 제외한 공부 시간을 합산하는 데 어려움을 겪을 수 있다.
- [가정] 달력상 며칠이 남았다는 사실만으로는 실제 작업 시간이 충분한지 판단하기 어렵다.
- [기대 효과] 필요한 시간과 가능한 시간을 같은 단위로 비교하면 부족분을 파악하고, 시간을 더 확보하거나 작업 계획을 조정하는 데 도움이 될 수 있다.

이 내용은 사용자 조사로 검증된 결론이 아니다. 사용자의 구체적인 과제 경험을 확인한 후 보완한다.

## 3. 대상 사용자와 핵심 문제

**확정한 대상 사용자:** 마감일이 정해진 개인 과제를 수행하면서, 남은 시간 안에 완료할 수 있을지 판단하려는 대학생.

**핵심 문제 가설:** 마감까지 남은 날짜와 실제 공부 가능한 시간이 다르기 때문에, 남은 작업량을 감당할 수 있는지 쉽게 판단하기 어렵다.

대표 사용자와 현재 해결 방법은 `02_user.md`에서 구체화한다. 첫 버전은 과제 하나를 비교하며 여러 과제의 동시 비교·자동 시간 배분은 포함하지 않는다.

## 4. 프로젝트 목적

사용자가 입력한 예상 작업 시간과 공부 가능한 시간을 비교하여, 마감 전 과제 수행에 필요한 시간이 부족한지 확인하고 자신의 계획을 조정할 수 있도록 돕는다.

결과는 입력값을 기준으로 한 시간 비교이며, 실제 완료 여부나 성적을 보장하는 예측은 아니다.

## 5. 핵심 이용 흐름 제안

1. 확인할 과제의 이름과 마감 날짜·시각을 입력한다.
2. **앞으로 남은 작업**에 필요한 예상 시간을 입력한다.
3. 지금부터 마감까지 해당 과제에 실제로 사용할 수 있는 시간을 입력한다.
4. 필요한 시간과 가능한 시간을 비교해 신호등 상태와 여유·부족 시간을 확인한다.
5. 시간 부족 시 확보 가능한 시간을 다시 검토하고 입력값을 수정해 결과를 다시 확인한다.

가능한 시간은 하루 평균 한 번만 입력하고 앱이 오늘부터 마감일까지 적용해 추정한다. 오늘은 지금 이후, 마감일은 마감 시각 이전의 실제 남은 시간을 넘지 않도록 제한한다. 다른 과제에 쓸 시간은 평균에서 제외하도록 안내한다.

### 시간 비교의 기본 원리

- 여유 시간 = 마감까지 해당 과제에 사용할 수 있는 시간 − 남은 예상 작업 시간
- [설명용 가상 예시] 필요한 시간이 8시간, 가능한 시간이 5시간이면 3시간 부족하다. 실제 사용자 경험이나 테스트 결과가 아니다.

| 신호 | 의미 | 합의한 기준 (A: 가능한 시간, N: 필요한 시간) |
|---|---|---|
| 초록 | 20% 이상 여유 | A ≥ 1.2 × N |
| 노랑 | 시간은 확보했지만 여유가 20% 미만 | N ≤ A < 1.2 × N |
| 빨강 | 시간 부족 | A < N |

20%는 사용자가 승인한 첫 버전의 기준이며 검증된 예측 기준은 아니다. 색상과 상태 이름, 필요한 시간·가능한 시간·여유 또는 부족 시간, 추정값 기준 안내를 함께 표시한다.

## 6. 목표와 성공 판단 기준 제안

아래 기준은 향후 확인할 목표이며, 현재 달성하거나 테스트한 결과가 아니다. 요구사항을 정할 때 고유 번호와 연결하고 `07_check.md`에 실제 결과를 기록한다.

| 목표 | 성공 판단 기준 제안 | 확인 방법 |
|---|---|---|
| 시간 부족을 수치로 확인 | 필요한 시간 8시간, 가능한 시간 5시간을 입력하면 부족 3시간이 표시됨 | 브라우저에서 입력·결과 확인 |
| 상태를 일관되게 구분 | 필요한 시간 10시간일 때 가능한 시간 9.5는 빨강, 10·11.5는 노랑, 12·12.5는 초록 | 경계값 시험 |
| 계획 변경을 반영 | 가능한 시간을 5시간에서 9시간으로 바꾸면 필요한 시간 8시간에 대해 여유 1시간으로 갱신됨 | 수정 후 재계산 확인 |
| 잘못된 입력을 처리 | 필수값 누락, 음수 시간, 지난 마감에 안내를 표시하고 정상 판단 결과처럼 제시하지 않음 | 입력 오류별 시험 |
| 결과를 이해할 수 있게 전달 | 사용자 본인이 테스트 후 신호 상태와 여유·부족 시간을 결과 화면에서 찾아 설명할 수 있음 | 실제 관찰과 사용자 답변 기록 |
| 로그인 없이 핵심 흐름 실행 | 배포 URL에 로그인하지 않고 접속해 입력·비교·수정 흐름을 완료함 | 배포 후 브라우저 확인 |

## 7. 포함·제외 범위 제안

MVP는 대표 사용자가 핵심 문제 하나를 처음부터 끝까지 해결할 수 있는 최소 버전이다. 대학생의 과제 하나에 대한 시간 비교는 사용자와 합의한 기본 범위다. 아래는 기획 당시의 후보이며, 요구사항별 구현·보류 결정은 `04_requirements_mvp.md`에 기록했다.

| 구분 | 범위 제안 | 이유와 영향 |
|---|---|---|
| 기본 범위 확정 | 한 번에 과제 하나의 필요한 시간과 가능한 시간 비교 | 사용자 승인. 구체적인 입력 방식은 후속 결정 |
| 포함 후보 | 신호등 상태와 여유·부족 시간 표시 | 사용자가 판단 근거를 이해할 수 있게 함 |
| 포함 후보 | 입력 수정과 재계산, 잘못된 입력 안내 | 계획 조정까지 핵심 흐름을 마무리하기 위함 |
| 제외 제안 | 회원가입, 로그인, 계정 간 동기화 | 로그인 없는 정적 웹앱이라는 제약을 유지함 |
| 첫 버전 제외 | 여러 과제 동시 비교·자동 시간 배분·우선순위 추천 | 한 과제 비교부터 시작하기로 합의. 사용자가 과제별 시간을 직접 배분해야 함 |
| 보류 제안 | 학교 과제·외부 달력 자동 연동, 알림 발송 | 외부 서비스 연동이 필요하며, 보류 시 사용자가 직접 입력·확인해야 함 |
| 보류 제안 | AI 기반 작업 시간 자동 추정 | 추정 정확도 검증이 필요하며, 보류 시 사용자가 예상 시간을 직접 정해야 함 |

20% 신호등 경계는 유지한다. 날짜별 시간 입력은 실제 사용자의 불편 피드백에 따라 하루 평균 입력으로 바꿨다. 이는 입력 부담을 줄이는 대신 날마다 다른 일정을 정확히 반영하지 못하는 추정 방식이다.

## 9. 제약과 진행 원칙

- HTML, CSS, JavaScript로 브라우저에서 실행하는 정적 웹앱을 만든다.
- 핵심 기능은 로그인, 서버, 비밀 API 키 없이 이용할 수 있게 한다.
- 과제지 표기 마감은 **2026년 12월 11일(금) 밤 12시**이다. 정확한 제출 마감 시각은 e-class에서 확인해야 한다.
- 사용자는 계획상 하루 2시간을 사용할 수 있다고 **가정**했다. `05_plan.md`는 이 가정으로 테스트·수정·배포·영상 제작 시간을 남겼다. 실제 투입 시간은 아직 확인되지 않았다.
- 공개 저장소에는 개인정보나 비밀 정보를 포함하지 않는다. 이후 업로드는 사용자가 직접 하거나 별도로 요청한 경우에 진행한다.
- 요구사항 후보 → 범위 선정 → 계획 → 설계 → 테스트를 같은 요구사항 번호로 연결한다.
- 테스트와 제출 완료 여부는 실제 확인한 결과만 기록한다.

## 10. 주요 위험과 대응 제안

| 위험 | 예상 영향 | 대응 제안 |
|---|---|---|
| 예상 작업 시간을 적게 입력 | 실제로 시간이 부족해도 여유 있다고 표시될 수 있음 | 추정값 기준임을 안내하고 남은 작업 시간을 수정할 수 있게 함 |
| 가능한 시간을 과대평가하거나 중복 계산 | 실제 확보 시간보다 결과가 낙관적으로 나옴 | 해당 과제에 쓸 수 있는 시간만 입력하도록 안내 |
| 마감 당일 시간을 잘못 포함 | 마감 후 시간까지 가능한 시간으로 계산될 수 있음 | 마감 날짜·시각을 받고 당일 시간 처리 규칙을 설계 단계에서 정의 |
| 노랑·초록 기준을 완료 보장으로 오해 | 결과를 과신할 수 있음 | 합의한 20% 기준과 추정의 한계를 설명하고 경계값을 시험 |
| 색상만으로 상태 전달 | 일부 사용자가 구분하기 어려움 | 상태 이름과 여유·부족 시간을 함께 표시 |
| 기능 범위가 계속 늘어남 | 테스트·배포 시간이 부족해짐 | 핵심 흐름을 우선하고 추가 기능은 보류 사유와 함께 관리 |

## 11. 확정한 결정과 다음 단계

1. 확정: 대상 사용자는 개인 과제를 수행하는 대학생이다.
2. 확정: 첫 버전은 과제 하나의 필요한 시간과 가능한 시간을 비교한다.
3. 실제 경험 자료가 없으므로 `02_user.md`에 가정임을 표시한 대표 사용자 시나리오를 작성한다.
4. 초기 날짜별 입력 방식은 하루 평균 입력으로 변경했다. 20% 신호등 기준과 REQ-01~08 번호는 유지하며, 현재 범위와 검증은 `04_requirements_mvp.md`·`07_check.md`에 기록한다.
